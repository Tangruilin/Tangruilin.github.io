SSD时代下LSM与B+树的演进对比

发表于 2026-03-23
本文字数： 1.4k 阅读时长 ≈ 5 分钟

本文由 AI 辅助编写

背景

LevelDB 作为 LSM Tree 的经典实现，其设计初衷是针对 HDD 时代「随机写慢、顺序写快」的特点进行优化。但随着 SSD 的普及，存储硬件的特性发生了根本性变化，LSM Tree 的优势是否依然存在？本文从 LevelDB 的演进出发，分析 LSM Tree 和 B+ 树在 SSD 时代的优劣对比。

HDD 时代：LSM 的绝对优势

在机械硬盘时代，随机写和顺序写的性能差距巨大：

LSM Tree 的核心思想就是将随机写转换为顺序写：写入先入 MemTable（内存），再批量刷盘。这个设计在 HDD 上带来了巨大的性能优势。

相比之下，B+ 树的随机写（页分裂、节点更新）在 HDD 上性能惨淡。

SSD 时代：LSM 优势被削弱

SSD 改变了硬件特性：

随机写和顺序写的差距大幅缩小，LSM 的核心优势减弱。

更严重的是，LSM 的 Compaction 机制带来严重的写放大：

相比之下，B+ 树的写放大只有 2-3 倍（主要是页分裂开销）。

SSD 时代初步对比

维度 LSM B+ 树
写放大 高（10-50x） 低（2-3x）
随机写优势 减弱 不明显
读延迟 不稳定（Compaction 抖动） 稳定
SSD 寿命 不友好 相对友好

在 SSD 普及初期，LSM 整体逊色于 B+ 树。

转机：Key-Value 分离

Key-Value 分离的 LSM 在随机写场景下重新获得优势：写放大低 + 磨损均匀。

范围查询：LSM 的软肋

Key-Value 分离并非万能，范围查询是其明显劣势：

场景 B+ 树聚簇索引 Key-Value 分离 LSM
范围查询 10 条 ~5 IO（顺序） ~10 IO（随机）
范围查询 100 条 ~8 IO（顺序） ~100 IO（随机）
范围查询 1000 条 ~15 IO（顺序） ~1000 IO（随机）

范围越大，差距越悬殊。这是 Key-Value 分离方案的核心代价。

总结

维度 B+ 树 LSM（传统） LSM（Key-Value 分离）
写放大 低（2-3x） 高（10-50x） 低（1-3x）
点查询 3-4 IO 1-多次 IO 1 IO（内存索引）
范围查询 快（聚簇索引） 中等 慢（随机 IO）
热点写入 有局部热点 均匀 均匀
SSD 寿命 中等 不友好 友好

结论：

  1. SSD 普及初期，LSM 因写放大问题整体逊色于 B+ 树
  2. Key-Value 分离让 LSM 重新获得竞争力：写放大降低、内存索引解决读取问题、追加写对 SSD 寿命友好
  3. 范围查询仍是 Key-Value 分离 LSM 的软肋，B+ 树聚簇索引在此场景下有明显优势

选型建议：

  • 点查询为主 + 写入密集 → Key-Value 分离 LSM
  • 范围查询为主 + 读密集 → B+ 树聚簇索引
  • 混合场景 → 根据实际负载测试选择

存储引擎的演进从未停止，LSM 和 B+ 树的边界也在逐渐模糊。理解各自优劣，才能在具体场景中做出正确选择。

LevelDB的未来演进方向

发表于 2026-03-23
本文字数： 909 阅读时长 ≈ 3 分钟

本文由 AI 辅助编写，作为后续深入探讨的引子。

背景

LevelDB 自 2011 年开源以来，已成为现代存储引擎的重要基石。RocksDB、Pebble 等项目都在其基础上演进。本文从架构角度分析 LevelDB 可能的演进方向。

1. 多线程化

现状：LevelDB 几乎是单线程的

演进方向：

组件 LevelDB RocksDB 已实现
写入 单线程 多线程 Write Batch Group
Compaction 单线程后台 多线程并行 Compaction
MemTable 单写 Concurrent SkipList

收益： 多核 CPU 利用率提升、吞吐量成倍增长。

2. Compaction 策略优化

现状：Leveled Compaction

问题：

  • 写放大严重（每层 10 倍放大）
  • Compaction 占用大量 IO

演进方向：

策略 特点 适用场景
Tiered Compaction 类似 Cassandra，写放大低 写多读少
FIFO Compaction 过期删除，无 Compaction 时序数据
Leveled + Tiered 混合 自适应选择 通用场景
Key-Range Compaction 按热点范围调度 热点不均匀

3. SSD / NVMe 优化

现状：LevelDB 为机械硬盘设计

  • Compaction 顺序读写 → 对 HDD 友好
  • 大块顺序 IO → SSD 上浪费并行度

演进方向：

HDD 优化 SSD/NVMe 优化
顺序写，避免随机写 并行 IO（多队列）
大块 IO 减少 Compaction 强度（SSD 随机读也快）
- 感知写放大对 SSD 寿命的影响
- io_uring / SPDK 避免内核开销

4. 持久内存（Persistent Memory）支持

现状：数据必须从内存刷到磁盘

演进方向：

已有研究项目：SLM-DB、LevelDB-PMem。

5. 存算分离 / 云原生

现状：单机嵌入式

演进方向：

优势：

  • 弹性扩缩容
  • 存储成本更低（对象存储）
  • 计算节点无状态

代表： Snowflake 的表格式、TiKV 的存算分离演进。

6. 向量化执行

现状：一次读取一个 KV

演进方向：

收益： OLAP 场景下大幅提升扫描性能。

7. 更丰富的数据模型

现状：纯 KV

演进方向：

数据模型 特点
Column Family 多列族（RocksDB 已有）
时序数据 TTL、自动降采样
文档模型 嵌套结构支持
图数据 节点/边存储优化

8. 内置事务支持

现状：只有原子写入

演进方向：

  • 快照隔离
  • 乐观并发控制 / 悲观锁
  • 跨 Key 事务

代表： RocksDB 事务 API、FoundationDB 的事务层。

演进路线图

总结

LevelDB 的演进本质是：从「单机嵌入式 KV」走向「现代存储引擎基础设施」。

硬件变化（SSD/NVMe/PMem）和工作负载变化（云原生/OLAP/时序）是主要驱动力。RocksDB 已经走了很远的路，但仍有优化空间。

后续会针对每个方向展开深入探讨。

leveldb的Arena内存池设计

发表于 2026-03-23
本文字数： 985 阅读时长 ≈ 4 分钟

背景

LevelDB 中实现了一个简单的内存池组件 Arena，用于 MemTable 的内存管理。本文分析 Arena 的设计意图以及它与通用内存分配器（如 tcmalloc）的区别。

Arena 的基本设计

Arena 的核心思想很简单：一次性分配大块内存，后续小分配直接从块中切分。

数据结构

内存布局

分配策略

Arena 默认使用 4KB 的块大小，分配时有两种路径：

  1. 快速路径（内联）：当前块剩余空间足够，直接指针偏移
  2. 慢速路径：当前块不够，申请新块
    • 大对象（>1KB）：单独分配一个块，避免浪费
    • 小对象（<=1KB）：申请新的 4KB 块，浪费当前块剩余空间

批量释放

Arena 最核心的特性是：不支持单独释放，析构时一次性释放所有内存。

Arena vs tcmalloc

一个自然的问题是：为什么不直接用 tcmalloc 这样的高性能内存分配器？

tcmalloc 的设计

tcmalloc 是通用内存分配器，采用分层设计：

小对象分配走 Thread Cache，不会陷入内核，性能已经很好。

那 Arena 的优势在哪？

关键在于：Arena 省的不是系统调用，而是 new/delete 调用本身和碎片管理开销。

假设分配 10000 个节点：

操作 tcmalloc Arena 差异
分配 ~10000 次 new ~122 次 new 省 98%
释放 ~10000 次 delete ~122 次 delete[] 省 98%

更关键的是，delete 比 new 更重：

tcmalloc 要支持任意生命周期对象的释放，必须维护 free list、合并碎片、可能归还内存。Arena 跳过了所有这些。

为什么 Arena 不需要线程安全？

Arena 没有任何锁：

因为 LevelDB 在更上层加锁：

写入本身就需要串行化（WAL、MemTable），顺带把内存分配也串行化了，Arena 内部不需要再加锁。

专用 vs 通用

tcmalloc Arena
服务任意生命周期 服务统一生命周期
必须支持单独释放 不支持单独释放
必须管理碎片 无碎片（整体销毁）
复杂的回收策略 极简：析构即清空

tcmalloc 的复杂性，Arena 根本不需要。

总结

Arena 的设计价值：

  1. 批量分配：减少 new 调用次数
  2. 批量释放：O(1) 释放，无碎片管理开销
  3. 缓存友好：连续内存，预取命中率高
  4. 极简实现：无锁、无外部依赖

Arena 是针对「同时生、同时死」对象群的特化设计，不是通用分配器的替代品。tcmalloc 优化的是分配本身，Arena 优化的是对象生命周期。两者可以共存：Arena 的底层仍然可以走 tcmalloc。
